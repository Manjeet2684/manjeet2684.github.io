Common Login Module (RBAC)

JWT authentication and role-based authorization

A reusable login boundary for Spring Boot APIs: the filter chain decides who you are, method security decides what you may call.

Stack
Java · Spring Boot · Spring Security · JJWT
Roles
USER · MODERATOR · ADMIN
Storage
JPA/Hibernate · H2 · BCrypt hashes
Source
Inspected locally from common_login.module

Problem

APIs need a login boundary that is reusable: register and login issue a token; subsequent requests carry that token; some routes are public, some need any authenticated user, some need ADMIN or MODERATOR.

Authentication vs authorization

Authentication answers “who is this?” (username/password → JWT). Authorization answers “may this principal hit this method?” (@PreAuthorize on roles). Mixing those in one controller check is how APIs leak; this module keeps them in the filter chain and method security.

JWT flow

POST /api/auth/register | /api/auth/login   (permitAll)
        → BCrypt verify/hash, AuthenticationManager
        → JwtService.generateToken(User)
        → AuthResponse { token, expiry, user, roles }

GET /api/...  Authorization: Bearer <jwt>
        → JwtAuthenticationFilter
        → load UserDetails, validate token
        → SecurityContextHolder
        → @PreAuthorize on controller methods

JwtAuthenticationFilter

OncePerRequestFilter. If there is no Authorization: Bearer header, the chain continues (public routes still work). Otherwise the filter extracts the username, loads UserDetails, checks token validity, and sets a UsernamePasswordAuthenticationToken into the security context. On parse/validation failure it clears the context and continues, so protected routes fail closed as unauthenticated rather than throwing from the filter.

CustomUserDetailsService

Implements Spring UserDetailsService and loads the JPA User by username. The User entity itself implements UserDetails.

BCrypt

PasswordEncoder bean is BCryptPasswordEncoder. Registration stores the encoded password; login goes through DaoAuthenticationProvider.

SecurityContextHolder

Request-level authentication is stored in the context after a valid JWT. Controllers can take @AuthenticationPrincipal User (see /api/auth/me).

User → Role model

Verified in source: User has an @ElementCollection of enum Role { USER, MODERATOR, ADMIN } stored in user_roles. Authorities are ROLE_ plus the enum name. There is no separate Permission entity and no many-to-many User–Role–Permission table in this codebase. Method security uses roles, not a permission catalog.

OAuth2

Not present in the inspected pom.xml or security config. This module is JWT resource-server style (JJWT), not an OAuth2 authorization-server or client flow. It is not an implemented dependency in this project.

Request lifecycle

  • Stateless sessions (SessionCreationPolicy.STATELESS).
  • CSRF disabled for the API; CORS defaults enabled.
  • Public: /api/auth/register, /api/auth/login, H2 console, /actuator/health.
  • Everything else authenticated. Filter sits before UsernamePasswordAuthenticationFilter.

Exception handling

GlobalExceptionHandler (@RestControllerAdvice) maps validation errors to 400, bad credentials to 401, access denied to 403, missing resources to 404, and a generic 500 that does not leak internals. Filter-chain 401/403 also write JSON ApiError bodies.

Database model

H2 runtime. users table with unique username and email. user_roles collection table. Demo data via DataInitializer. Not PostgreSQL in this module.

Method security examples

  • GET /api/users — hasRole('ADMIN')
  • GET /api/users/{id} — admin or self (#id == principal.id)
  • GET /api/admin/dashboard — ADMIN
  • GET /api/moderator/reports — MODERATOR or ADMIN

Security considerations

  • Passwords never stored in plaintext.
  • JWT secret via JwtProperties (must not ship a production secret in source).
  • H2 console is permitted in this demo — disable that outside local use.
