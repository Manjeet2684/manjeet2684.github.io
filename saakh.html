SAAKH

Financial transfer and reconciliation backend

A Spring Boot monolith where PostgreSQL is the source of truth and Kafka is used only after commit, through a transactional outbox.

What problem this solves

Posting APIs fail in ordinary ways: client retries, duplicate requests, concurrent debits, and a second write to a message broker. SAAKH is built so those cases stay visible and testable instead of becoming silent double-moves or missing events.

Why transfer correctness matters

Money movement is not “eventually consistent enough.” A crash halfway through a debit/credit pair, or a retry that posts twice, is a ledger bug. SAAKH keeps the books in PostgreSQL and treats Kafka as an after-commit notification path, not a second ledger.

Architecture overview

Client --HTTP--> Spring Boot monolith
                     |
                     |  TX A: posting (PostgreSQL only)
                     v
              PostgreSQL (source of truth)
                     |
                     |  after commit
                     v
              TX B: outbox publisher --at-least-once--> Kafka topic saakh.transfers

There is no Kafka consumer in this project and no notification writer. Kafka is producer-only.

Money-movement transaction (TX A)

One PostgreSQL transaction posts the transfer. Inside that transaction:

  • Lock both accounts (see concurrency).
  • Validate, debit source, credit destination.
  • Write the transfer record.
  • Write immutable double-entry ledger lines (DEBIT and CREDIT).
  • Insert an unpublished outbox row (event ID assigned here).
  • Insert the idempotency record.
  • Commit. HTTP 201.

Kafka is not called in TX A.

Concurrency control

Account rows are locked with ordered SELECT … FOR UPDATE (lock by account id order) so concurrent A→B and B→A cannot deadlock, and cached balances cannot be lost under overlapping transfers.

Idempotency

Clients send an Idempotency-Key. The request body is fingerprinted with SHA-256. Same key + same body replays the original transfer (HTTP 201, money does not move twice). Same key + different body returns HTTP 409. Missing key returns 400.

Transactional outbox

The unpublished outbox row is committed with the money. After that commit, a separate publisher (TX B) selects unpublished rows with FOR UPDATE SKIP LOCKED, produces to Kafka, and sets published_at only after acknowledgement. Publish failure leaves published_at null so a later batch can retry.

Kafka / at-least-once semantics

Delivery to Kafka is at-least-once, not exactly-once. Events have stable event IDs assigned at insert. transferId is the partition key. If Kafka acks and the process crashes before published_at commits, the same eventId may be published again. There is no consumer-side deduplication and no XA.

Reconciliation

Detect-only. Settlement ingest is fingerprint-protected. Reconciliation classifies MATCHED / MISSING_EXTERNAL / MISSING_INTERNAL / amount or currency mismatch / duplicate external. It never moves money and never rewrites ledger, transfer, or outbox rows.

Testing

47 automated tests, including Testcontainers-backed API tests (PostgreSQL, and Kafka for outbox publisher tests). GitHub Actions runs the suite and builds a local image. It does not deploy.

Operational considerations

  • Request IDs on X-Request-ID, copied into MDC logs. Invalid IDs are replaced; the request is not rejected.
  • Micrometer in-process; Actuator exposure is health only. Readiness is process + PostgreSQL. Kafka is not in the readiness group.
  • Docker Compose for PostgreSQL and Kafka. Two API-key audiences (client vs internal); SHA-256 compared with MessageDigest.isEqual.

What this project does not claim

Not claimed: production banking platform, UPI switch, Razorpay clone, microservices, exactly-once Kafka, invented TPS/latency/volume, live production traffic, automatic ledger repair, PSP integration.
