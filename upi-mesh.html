UPI Offline Mesh Payment System

Mesh-routed deferred settlement — simulation

A Spring Boot backend plus a software mesh. Encrypted packets hop untrusted devices until a bridge uploads them. This is not NPCI, not a UPI switch, and not a live payment network.

Label: simulation / teaching demo. H2 in-memory database. Idempotency cache is a JVM ConcurrentHashMap (Redis SETNX analogue), with a unique packet-hash constraint as a second line of defense.

Real-world motivation

There are places with no useful uplink: basement, metro, festival crowd. The interesting question is whether a payment instruction can travel through nearby phones and still settle once when some device finally reaches the internet.

Offline payment problem

The receiver cannot verify funds offline. A packet in transit is an IOU until the backend settles. The README is explicit: this is deferred settlement, not “real-time offline UPI.”

Mesh simulation

Virtual devices gossip packets with a TTL. A designated bridge with hasInternet=true POSTs ciphertext to /api/bridge/ingest. There is no real Bluetooth stack in this project.

Sender phone (offline)
  encrypt PaymentInstruction → MeshPacket
        |
        v  gossip hops (simulated BLE)
  stranger devices  →  bridge walks “outside”
        |
        v  HTTPS POST /api/bridge/ingest
  hash → claim → decrypt → freshness → settle

Threat model

  • Untrusted hops must not read amount or parties.
  • Bit-flips in ciphertext must not settle.
  • Several bridges uploading the same packet must not debit twice.
  • An old captured ciphertext must not replay after the freshness window.

Encryption: RSA-OAEP + AES-256-GCM

Hybrid cryptography: a fresh AES-256 key encrypts the JSON with AES-256-GCM (confidentiality + GCM tag for tamper detection). That AES key is wrapped with RSA-OAEP using the server’s public key. Intermediaries see opaque ciphertext. Tampering fails GCM verification before settlement.

Freshness / replay protection

The encrypted payload includes signedAt (rejected if older than the configured window, 24 hours in the demo) and a nonce. Changing those fields without the key breaks the GCM tag. A replay of the same ciphertext is byte-identical, so the hash claim catches it.

SHA-256 hashing

The server hashes the ciphertext first, before RSA. Dedupe key is the ciphertext hash, not a rewritable packet id and not the cleartext (which would require decrypting first).

Duplicate delivery handling

IdempotencyService.claim(hash) uses atomic putIfAbsent. One concurrent claimer proceeds to decrypt and settle; others are dropped as duplicates. A unique index on transactions.packet_hash backs this if the cache layer is wrong. This is single-process atomic claim, not distributed exactly-once processing. Do not read it as Kafka exactly-once or as a production multi-node guarantee.

Settlement simulation

@Transactional debit + credit + ledger insert. Accounts use @Version optimistic locking as defense in depth. Ledger is H2, seeded in memory.

Limitations

  • No proof of funds offline; double-spend across two basements is inherent to the concept.
  • RSA keypair is regenerated on startup — not an HSM.
  • No auth on the bridge ingest endpoint in the demo.
  • Bluetooth in real life is much harder than the simulator.

Technology stack

Java 17+, Spring Boot, JPA, H2, hybrid RSA-OAEP + AES-256-GCM, SHA-256, in-memory idempotency cache, concurrency test for three simultaneous bridge ingestions.
